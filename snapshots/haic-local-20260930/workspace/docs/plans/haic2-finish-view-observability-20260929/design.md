# Pixel return-to-start observability before a missed finish

The consumed TUNE student run 2:5205 reached progress 1.0 but did not validly cross the finish line and later departed the road. This run tests whether the observation stream itself provides a useful repeated-start-view signal before that failure. It does not change any driving action. The sensor pools normalized grayscale pixels from rows 12–59 and columns 8–75 into 12×17 values, compares each frame with the reset view and the first twelve even-numbered driving views, and requires at least five visible road-center rows. A view is similar when mean absolute pixel difference is at most 0.035 and mean road-center displacement at most 3 pixels. Three consecutive similar decisions after decision 120 form a revisit signal. This rule is frozen before execution.

Run the unchanged pixel student on consumed 1:5200 (valid finish) and 2:5205 (missed finish), plus the selected stable pixel driver on 2:5205 (valid finish). These are three diagnostic episodes on two consumed TUNE identities, at most 2,000 decisions each in Linux CPU and 900 seconds. Capture full action, speed, pixel-distance and finish traces. The signal is worth implementing in a controller only if it occurs at least 15 decisions before the failed student's terminal event, while neither successful run fires it more than 15 decisions before its valid finish. Otherwise reject this observable and pivot; do not tune image distance or persistence on these cells. Evaluation progress/finish fields are diagnostic labels only and never enter the runtime sensor. No new competitive evidence or external action.
